# Architectural Invariants — Engineering Society Platform

Every invariant states **what must always be true**, **where it is implemented**,
**where it is tested**, **where it is documented**, and its **status**.

## Status legend

| Status                | Meaning                                                                                                           |
| --------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **PROVEN**            | Enforced in the database or in code, **and** covered by an automated test that would fail if the invariant broke. |
| **ENFORCED-UNTESTED** | Implemented correctly, but no automated test would catch a regression.                                            |
| **APP-ONLY**          | Enforced only in application code, so a direct database client could bypass it.                                   |
| **DOC-ONLY**          | Asserted in documentation but not implemented or not verifiable.                                                  |
| **GAP**               | An invariant that _should_ exist but is missing or only partially implemented.                                    |

`tests/` paths are relative to the repository root. Migration line references are
to `db/migrations/`.

## A. Access-control invariants

### I-01 — A Committee Manager has exactly one committee

|                    |                                                                                                                                                                                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | An ordinary manager can never hold two committee assignments, and a global role (Board/Technical) never carries a `committee_id`.                                                                                                                                                           |
| **Implementation** | `administrative_access` has a **single-column primary key on `user_id`** (`0016:58`) and `CHECK administrative_access_scope_check`: `(access_level = 'COMMITTEE_MANAGER') = (committee_id IS NOT NULL)` (`0016:67-68`). `private.change_administrative_access` re-validates (`0023:27-29`). |
| **Test coverage**  | `tests/db/access-hierarchy.test.ts` (scoping 177-285); `tests/db/access-lifecycle.test.ts` (rejection matrix 109-125); `tests/user-actions.test.ts` (one-committee validation 194-210).                                                                                                     |
| **Documentation**  | ADR 0012; `docs/ACCESS_CONTROL.md`; `docs/UC-02_Data_and_Security.md`; `lib/access/README.md`.                                                                                                                                                                                              |
| **Status**         | **PROVEN** — enforced by primary key + CHECK, tested at three layers.                                                                                                                                                                                                                       |

### I-02 — Board Administration has global operational scope but no access-management authority

|                    |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | `BOARD_ADMIN` can operate every committee's events, registrations and exports, but cannot grant, revoke, reassign or escalate any access.                                                                                                                                                                                                                                                                                                                                                             |
| **Implementation** | Scope: `private.can_access_committee` returns true for `access_level IN ('BOARD_ADMIN','TECHNICAL')` (`0016:108`). Authority denial: every access mutation routes through `private.change_administrative_access` / `change_technical_access` / `replace_committee_manager`, each requiring an active **TECHNICAL** actor (`0023:19-22`, `0019:30-33`); plus `requireTechnical()` in `app/admin/(protected)/access/user-actions.ts` and an `accessLevel !== "TECHNICAL"` guard in `access/actions.ts`. |
| **Test coverage**  | `tests/db/access-hierarchy.test.ts` (Board scoping 177-285; ownership transfer 447-483); `tests/user-actions.test.ts` (every operation denied for Board/Manager/anonymous 118-161); `tests/access-actions.test.ts`.                                                                                                                                                                                                                                                                                   |
| **Documentation**  | ADR 0012; `docs/ACCESS_CONTROL.md`; `lib/access/README.md`; `lib/auth/README.md`.                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Status**         | **PROVEN** — enforced in SQL and covered by denial tests.                                                                                                                                                                                                                                                                                                                                                                                                                                             |

### I-03 — Technical owns access control, and that authority comes from the access level only

|                    |                                                                                                                                                                                                                                                                                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Description**    | Only `access_level = 'TECHNICAL'` confers access-management authority. The existence of a committee named "Technical Team", a matching slug, membership in it, an email address, or Auth metadata must never grant authority.                                                                                                                          |
| **Implementation** | `private.change_*_access`, `replace_committee_manager`, `list_auth_directory`, `record_auth_admin_action` all predicate on `actor.access_level = 'TECHNICAL' AND actor.revoked_at IS NULL` (`0021:40-42`, `0021:89-92`, `0023:19-22`). `adminClient()` in `lib/auth/admin.ts` is reachable only from actions that already passed `requireTechnical()`. |
| **Test coverage**  | `tests/db/maintenance-grants.test.ts` (role matrix 65-83); `tests/db/auth-user-directory.test.ts` (Technical-only fields 28-54); `tests/user-actions.test.ts` (118-161).                                                                                                                                                                               |
| **Documentation**  | ADR 0012 ("Technical authority comes from the explicit access level, never from the Technical Team committee name, slug, or membership"); `docs/ACCESS_CONTROL.md`; `lib/auth/README.md` ("Never branch on a specific email").                                                                                                                         |
| **Status**         | **PROVEN** — no code path branches on a name, slug or email (grep-verified: zero email literals in authorization code).                                                                                                                                                                                                                                |

### I-04 — The last active Technical identity cannot be removed

|                    |                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | The platform can never be left with zero active Technical administrators, including via self-removal or the external maintenance path.                                                                                                                                                                                                                                |
| **Implementation** | `private.change_technical_access`: `IF (SELECT count(*) FROM public.administrative_access WHERE access_level = 'TECHNICAL' AND revoked_at IS NULL) <= 1 THEN RETURN 'LAST_TECHNICAL_ADMIN'` — present **twice** (`0019:59-62` and `0019:117-120`), covering both the grant-then-revoke and direct-revoke shapes. The same guard exists on the `app_maintenance` path. |
| **Test coverage**  | `tests/db/access-lifecycle.test.ts` "last-Technical-owner invariant under concurrency" (263-285); `tests/db/access-hierarchy.test.ts` "final owner cannot be removed by runtime or maintenance" (523-552).                                                                                                                                                            |
| **Documentation**  | ADR 0012; ADR 0014; `docs/Platform_Maintenance_Runbook.md` ("LAST_TECHNICAL_ADMIN blocks removal of the final active Technical identity, including self-removal").                                                                                                                                                                                                    |
| **Status**         | **PROVEN** — enforced under the global access lock and tested concurrently.                                                                                                                                                                                                                                                                                           |

### I-05 — Self-escalation is impossible through any application path

|                    |                                                                                                                                                                                                                                                                                                            |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | A user cannot grant themselves a higher access level, and Technical access cannot be granted through the ordinary administrative routine.                                                                                                                                                                  |
| **Implementation** | `IF p_actor = p_user THEN RETURN 'SELF_ESCALATION'` (`0019:43`); `change_administrative_access` rejects `p_level = 'TECHNICAL'` outright (`0023:27-29`); Technical changes are only reachable through `change_technical_access` (app, TECHNICAL actor) or `set_technical_access` (`app_maintenance` only). |
| **Test coverage**  | `tests/db/routines-and-authorization.test.ts` "self-grant denial" (408-438); `tests/db/access-hierarchy.test.ts`; `tests/user-actions.test.ts` (self-targeting refused 473-496).                                                                                                                           |
| **Documentation**  | ADR 0012 ("Neither a manager nor a board user can promote themselves"); `docs/ACCESS_CONTROL.md`.                                                                                                                                                                                                          |
| **Status**         | **PROVEN**                                                                                                                                                                                                                                                                                                 |

### I-06 — Revocation is immediate for authorization, while the identity and history are retained

|                    |                                                                                                                                                                                                                                                                   |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | Setting `revoked_at` removes all authority on the very next request, but never deletes the Auth identity, the historical grant row, the audit trail, or the actor's past attribution. Former role/committee become historical metadata only.                      |
| **Implementation** | Every authorization predicate includes `revoked_at IS NULL` (`0016:107`, `0016:131`, `0016:149`, `0021:41`, `0023:21`). Revocation is an `UPDATE ... SET revoked_at = now(), revoked_by = p_actor` — no `DELETE` grant exists for any role on any business table. |
| **Test coverage**  | `tests/db/routines-and-authorization.test.ts` (revoked grants 162-193); `tests/db/m8-consistency.test.ts` (revocation clears every read 15-79); `tests/db/access-hierarchy.test.ts`; `tests/manager-context.test.ts` (revocation between reads).                  |
| **Documentation**  | ADR 0014; `docs/ACCESS_CONTROL.md`; `lib/access/README.md`.                                                                                                                                                                                                       |
| **Status**         | **PROVEN**                                                                                                                                                                                                                                                        |

### I-07 — Revoked identities are ineligible for Auth deletion while any historical reference exists

|                    |                                                                                                                                                                                                                                                    |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | An Auth user who appears anywhere in history — grants, event actors, audit JSON target ids — must not be deleted, and references must never be removed to make deletion pass.                                                                      |
| **Implementation** | **Procedural, not enforced.** The schema makes deletion _fail_ naturally: every FK to `auth.users` is `ON DELETE no action` (`0003:53-56`, `0003:60`), and audit rows are never deleted. `USER_HAS_HISTORY` is a documented policy, not a routine. |
| **Test coverage**  | **None.** No test exercises the deletion-eligibility rule.                                                                                                                                                                                         |
| **Documentation**  | ADR 0014 ("A retained revoked grant/history makes a user ineligible (USER_HAS_HISTORY). Never delete references to make deletion pass."); `docs/Platform_Maintenance_Runbook.md` (exceptional-deletion gate).                                      |
| **Status**         | **ENFORCED-UNTESTED** — foreign keys enforce the _effect_; the policy itself has no automated test.                                                                                                                                                |

### I-08 — Authentication is not authorization

|                    |                                                                                                                                                                                                                                                                                                                      |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | Possessing a valid password, a confirmed email, or a live session confers **no** administrative capability. Only an active `administrative_access` row does.                                                                                                                                                         |
| **Implementation** | `resolveManagerContext` (`lib/auth/manager.ts`) returns `{ kind: "unassigned" }` when no active grant row is found, and the protected layout renders `NoAccessState` instead of the dashboard. Account creation (`createUserAction` with `level: "NONE"`) explicitly grants nothing.                                 |
| **Test coverage**  | `tests/manager-context.test.ts` (45-111); `tests/access-boundaries.test.tsx` (protected layout and Technical page refuse retained/Board identities, 44-66); `tests/user-actions.test.ts` (retained identity without access 97-116); `tests/e2e/admin-auth.spec.ts` (unauthenticated boundary for every admin route). |
| **Documentation**  | ADR 0012; ADR 0013 ("an Auth user is an identity; administrative_access is authorization. Creating an account grants nothing"); ADR 0014; `docs/ACCESS_CONTROL.md`.                                                                                                                                                  |
| **Status**         | **PROVEN**                                                                                                                                                                                                                                                                                                           |

## B. Database-security invariants

### I-09 — `app_runtime` has no direct DML on any table

|                    |                                                                                                                                                                                                                                                                                                                                                |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | The application's runtime database role cannot read or write a business table directly. All access is through fixed `private.*` routines.                                                                                                                                                                                                      |
| **Implementation** | `0004` states the intent (`0004:79-80`) and the DDL matches: across all 24 migrations, every `... TO app_runtime` statement is either `GRANT USAGE ON SCHEMA` or `GRANT EXECUTE ON FUNCTION`. `REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon, authenticated, PUBLIC` (`0004:49`) plus `ALTER DEFAULT PRIVILEGES` revokes (`0004:50-51`). |
| **Test coverage**  | `tests/db/app-runtime-security.test.ts` — asserts no `BYPASSRLS`, and denied SELECT/INSERT/UPDATE/DELETE across **10 tables**, denied `CREATE` in `private`, denied execution of an unapproved `SECURITY DEFINER` routine (10-78).                                                                                                             |
| **Documentation**  | `db/README.md`; `docs/UC-02_Data_and_Security.md` ("The runtime login is NOBYPASSRLS, owns no tables/functions, cannot provision roles, and has no direct business-table INSERT/UPDATE/DELETE"); `lib/events/README.md`; `lib/registrations/README.md`.                                                                                        |
| **Status**         | **PROVEN** — verified in the DDL by this audit _and_ by an explicit denial test.                                                                                                                                                                                                                                                               |

### I-10 — RLS is enabled and forced on every table reachable from an exposed schema

|                    |                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | Any table an anon-key or authenticated client could reach is protected by row-level security, and a table without policies is default-deny.                                                                                                                                                                                                                      |
| **Implementation** | `0006:6-25` enables **and forces** RLS on all ten public tables plus `private.uc02_audit`; `0004:88-91` and `0004:141` cover the tables added later. Policies: `anon_select_visible_events` (`0004:96-98`), `authenticated_select_own_grants` (`0004:123-125`), `authenticated_select_admin_events/registrations/committees` (`0016:158-166`).                   |
| **Test coverage**  | `tests/rls-staging-anon.test.ts` — **live anon-key client against the real staging project**, proving both directions: published events readable, draft events invisible, non-public columns denied `42501`, `members` denied outright, and anon INSERT into `registrations` denied. `tests/db/jwt-claims-policy.test.ts` proves authenticated visibility rules. |
| **Documentation**  | `CLAUDE.md` ("Row-level security is not optional… Policies ship in the same migration as the table"); `docs/UC-02_Data_and_Security.md` §6-7; ADR 0006.                                                                                                                                                                                                          |
| **Status**         | **PROVEN** — but see audit finding F-02: the live staging proof **throws at import** without credentials, so on a clean clone the coverage silently becomes zero rather than failing loudly.                                                                                                                                                                     |

### I-11 — `SECURITY DEFINER` routines are a deliberate, narrow capability boundary

|                    |                                                                                                                                                                                                                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Description**    | Every privileged routine pins a fixed `search_path`, uses schema-qualified references, contains no dynamic SQL, has `EXECUTE` revoked from `PUBLIC`, and is owned by a dedicated NOLOGIN role rather than the table owner or a superuser.                                                                                            |
| **Implementation** | All **69** `SECURITY DEFINER` functions set `SET search_path = public, pg_temp` (**67** explicit occurrences; the remaining two inherit the identical clause on the same statement). `ALTER FUNCTION ... OWNER TO uc02_routine_owner` (51 statements). Zero `SECURITY INVOKER` functions. Per-function `REVOKE ALL ... FROM PUBLIC`. |
| **Test coverage**  | `tests/db/app-runtime-security.test.ts` (unapproved routine denied, approved allowed, 60-78); `tests/db/maintenance-grants.test.ts` (audit-constraint rollback 85-103).                                                                                                                                                              |
| **Documentation**  | `docs/UC-02_Data_and_Security.md` ("SECURITY DEFINER is an intentional capability boundary, not a permission-error workaround"); `db/README.md`.                                                                                                                                                                                     |
| **Status**         | **PROVEN**                                                                                                                                                                                                                                                                                                                           |

### I-12 — `EXECUTE` on privileged routines is granted only as designed

|                    |                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | `anon`, `authenticated` and `service_role` cannot invoke any mutation routine; `authenticated` may invoke exactly one read helper.                                                                                                                                                                                                                                                                                     |
| **Implementation** | `app_runtime` holds `EXECUTE` on 28 routines; `app_maintenance` holds exactly one (`private.set_technical_access`, `0016:1105`); `authenticated` holds exactly one (`private.can_access_own_committee`, `0016:122` / `0022:23`); `anon`, `service_role` and `PUBLIC` hold none. Four helpers (`can_access_committee`, `lock_committee_access`, `can_review_event`, `public_event_availability`) have no grants at all. |
| **Test coverage**  | `tests/db/maintenance-grants.test.ts` (anon/authenticated/service_role denied, 65-83); `tests/db/admin-event-detail.test.ts` ("anon/authenticated cannot execute", 33-109); `tests/db/access-lifecycle.test.ts` (routine execute-only grants 248-261).                                                                                                                                                                 |
| **Documentation**  | `docs/UC-02_Data_and_Security.md` ("Only runtime login may execute approved public/admin routines; maintenance routines have a separate grant"); `db/README.md`.                                                                                                                                                                                                                                                       |
| **Status**         | **PROVEN**                                                                                                                                                                                                                                                                                                                                                                                                             |

### I-13 — Attendee PII is never public

|                    |                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | Names and emails of registrants are never exposed on a public surface, never readable with the anon key, and never included in a public payload.                                                                                                                                                                                                                                                                                        |
| **Implementation** | `anon` holds **no** privilege on `registrations` (`0004:49` revokes all; `0004:60` grants a column-level SELECT on `events` only). The public read routines (`private.list_public_events`, `private.get_public_event`) return only `id, title, description, event_date, location, committee_name, availability` — never counts, capacity or committee ids. Admin registration data is reachable only through committee-scoped routines. |
| **Test coverage**  | `tests/db/public-event-reads.test.ts` (public DTO only, draft hidden, availability derived without counts, 11-51); `tests/rls-staging-anon.test.ts` (anon cannot read or write `registrations` at all); `tests/db/admin-registration-operations.test.ts`.                                                                                                                                                                               |
| **Documentation**  | ADR 0006; `docs/UC-02_Data_and_Security.md` §6-7 ("Public raw columns are id/title/description/event_date/location only… no SELECT *"); `lib/events/README.md` ("the public surface never receives raw status, capacity, counts, or committee IDs"); `lib/admin-registrations/README.md`.                                                                                                                                               |
| **Status**         | **PROVEN**                                                                                                                                                                                                                                                                                                                                                                                                                              |

### I-14 — Cross-committee access is denied for every read and write

|                    |                                                                                                                                                                                                                                                                                                                                                      |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | A committee manager can only ever see or affect their own committee's events, registrations, counts and exports — and a foreign id must look identical to a nonexistent one.                                                                                                                                                                         |
| **Implementation** | One predicate is used everywhere: `private.can_access_committee` for reads (`0016:659, 730, 755, 770, 803, 846`) and `private.lock_committee_access` for writes (`0016:469-471` and the six lifecycle routines). RLS uses the same predicate for browser reads (`0016:158-166`). Out-of-scope ids return `NOT_FOUND`, never a distinguishable error. |
| **Test coverage**  | `tests/db/access-hierarchy.test.ts` (per-committee scope isolation 337-389; manager vs Board/Technical scoping 177-285); `tests/db/admin-event-detail.test.ts`; `tests/db/admin-registration-operations.test.ts`; `tests/admin-registration-export.test.ts` (foreign event 404).                                                                     |
| **Documentation**  | ADR 0012; `docs/UC-02_Data_and_Security.md` §5; `lib/admin-events/README.md` ("a malformed, missing or out-of-scope id returns null (404)").                                                                                                                                                                                                         |
| **Status**         | **PROVEN**                                                                                                                                                                                                                                                                                                                                           |

### I-15 — Malformed identifiers are safe

|                    |                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | A malformed UUID must never reach the database and must produce the same outward result as a missing record.                                                                                                                                                                                                                                                                             |

### I-16 — The audit trail is append-only and fully attributed

|                    |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Description**    | Every event, registration, grant and access change is recorded permanently, with enough context to reconstruct who did what to which record, under the same transaction as the change.                                                                                                                                                                                                                                                                                                                             |
| **Implementation** | `private.uc02_audit` with `id, occurred_at, committee_id, event_id, registration_id, actor_kind, actor_user_id, action, changes (jsonb)`. Append-only is enforced **by grant**: `uc02_routine_owner` gets only `SELECT, INSERT` (`0004:71`) and `app_maintenance` only `SELECT` after (`0010:22`) — no role holds `UPDATE`/`DELETE`/`TRUNCATE`. `changes` carries `before`/`after` for event edits and `previous`/`next` for access changes. Migration actors are recorded honestly as `actor_kind = 'migration'`. |
| **Test coverage**  | `tests/db/routines-and-authorization.test.ts` (approval chain + audit **order**, 195-261; audit atomicity and rollback, 440-476); `tests/db/access-lifecycle.test.ts` (audit pairing 43-107; audit-failure rollback via a temporary trigger 180-201); `tests/db/admin-registration-operations.test.ts` (exactly one `registrations.exported` row).                                                                                                                                                                 |
| **Documentation**  | `docs/UC-02_Data_and_Security.md` ("Every event/registration/grant create or change is logged atomically… Audit failure rolls back business writes"); `db/README.md` ("permanent, append-only mutation history").                                                                                                                                                                                                                                                                                                  |
| **Status**         | **PROVEN** for all routine paths. **GAP for non-routine paths:** the guarantee holds only for updates that go through the routines — no trigger prevents an owner-privileged `UPDATE` from skipping the audit row.                                                                                                                                                                                                                                                                                                 |

### I-17 — Audit records never contain secrets

|                    |                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | No password, token, hash, recovery link or unbounded user object is ever written to the audit trail.                                                                                                                                                                                                                                                                                                             |
| **Implementation** | `private.record_auth_admin_action` accepts only a fixed action label plus a `detail` string validated by `char_length(v_detail) > 60 OR v_detail !~ '^[a-z0-9_ .-]+$'` → `VALIDATION_ERROR` (`0021:85-87`). The TypeScript type is a closed union (`AuthAdminAction`) and callers pass only literal words such as "invitation", "temporary password", "no email". Password inputs are never passed to `audit()`. |
| **Test coverage**  | `tests/db/auth-user-directory.test.ts` ("refusal of secret-carrying details", 84-137); `tests/user-actions.test.ts` (password never persisted in results or mocks, 356-391, 450-471; audit-failure handling without leaking a secret, 247-326).                                                                                                                                                                  |
| **Documentation**  | ADR 0013 ("whose actions are fixed labels with a short, character-restricted detail so a secret cannot be stored"); `docs/UC-02_Data_and_Security.md` ("Do not put raw IPs, tokens or unbounded user-provided objects in audit JSON").                                                                                                                                                                           |
| **Status**         | **PROVEN** — enforced by a database guard _and_ a closed TypeScript union _and_ covered by tests.                                                                                                                                                                                                                                                                                                                |

### I-18 — Raw IP addresses are confined to rate-limit bookkeeping

|                    |                                                                                                                                                                                                                                                           |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | A registrant's IP is used for abuse prevention and never enters permanent audit history.                                                                                                                                                                  |
| **Implementation** | IPs live only in `public.registration_attempts` (`ip_address inet`, indexed by `(ip_address, created_at)`). The audit table has no IP column. `app_maintenance` holds the only `DELETE` in the schema, on that table (`0004:77`), as the purge mechanism. |
| **Test coverage**  | Indirect: `tests/db/registration-concurrency.test.ts` exercises the limiter; **no test asserts absence of IP in audit**.                                                                                                                                  |
| **Documentation**  | `docs/UC-02_Data_and_Security.md` §"PII" ("Raw IPs stay only in private limiter bookkeeping… not appended into permanent audit history"); ADR 0005; decision D10.                                                                                         |
| **Status**         | **ENFORCED-UNTESTED** for the absence claim. **GAP:** no retention job exists — the table grows unbounded, so "purged after one hour" is a design intent, not an implemented behaviour.                                                                   |

## C. Domain invariants

### I-19 — Registration capacity cannot be oversubscribed

|                    |                                                                                                                                                                                                                                                                                                                                                |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | Confirmed registrations can never exceed capacity, even under genuine concurrent submission for the final seat.                                                                                                                                                                                                                                |
| **Implementation** | `private.register_for_event` takes `SELECT ... FROM public.events WHERE id = ... FOR UPDATE` and re-checks state and confirmed count **after** acquiring the lock. `hold_event_full` and `edit_event` take the same event lock, and `edit_event` refuses capacity below the confirmed count (`CAPACITY_BELOW_COUNT`, `0016:437-439, 567-569`). |
| **Test coverage**  | `tests/db/registration-concurrency.test.ts` — a **real parallel capacity-1 oversubscription race** (79-115).                                                                                                                                                                                                                                   |
| **Documentation**  | `docs/UC-02_Data_and_Security.md` §"concurrency" (event-first `FOR UPDATE` locking); decision D08; ADR 0008.                                                                                                                                                                                                                                   |
| **Status**         | **PROVEN**                                                                                                                                                                                                                                                                                                                                     |

### I-20 — At most one active registration per event and normalized email

|                    |                                                                                                                                                                                                                                                                                                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**    | The same email cannot hold two active places (confirmed or waitlisted) for one event, and a repeat attempt must not overwrite the existing identity.                                                                                                                                                                                                          |
| **Implementation** | Partial unique index `registrations_active_event_email_idx` on `(event_id, attendee_email) WHERE status IN ('confirmed','waitlisted')` (`0003:69`), backed by `CHECK registrations_email_canonical` (`0003:82`) so the stored value is already `lower(btrim(...))`. The routine catches `unique_violation` and returns `ALREADY_REGISTERED` (`0005:107-109`). |
| **Test coverage**  | `tests/db/registration-concurrency.test.ts` — normalization and single active registration (17-44) plus a **real parallel duplicate race** (46-77).                                                                                                                                                                                                           |

### I-23 — Every mutation is revision-locked; no silent last-write-wins

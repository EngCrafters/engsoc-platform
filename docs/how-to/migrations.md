# Migrations

How the schema is versioned, what the repository can apply, what is known to be applied where,
and how to add a migration safely. Read [`db/README.md`](../../db/README.md) for the history of
the early migrations, and the project rule in `CLAUDE.md`: **never run migrations or seed data
against production** without explicit owner approval.

## Files and ordering

- [`db/migrations/`](../../db/migrations/) holds 41 SQL files, `0000_initial_schema.sql` to
  `0040_permission_management_own_groups.sql`, applied strictly in numeric order.
- [`db/migrations/meta/_journal.json`](../../db/migrations/meta/_journal.json) lists each one
  (`idx`, `tag`, `when`). The highest `idx` (40) is the schema version the code requires
  (`REQUIRED_SCHEMA_VERSION`).
- `0000`, `0001` and `0003` were generated by `drizzle-kit generate`. Every other migration is
  hand-written SQL: roles, grants, RLS, routines, data-preserving changes. Snapshots in
  `meta/` exist only for `0000`–`0004`.
- From **0030** on, each migration replaces `private.core_schema_version()` to return its own
  number. `/v1/health` and the release gate compare that number with the journal. Before 0030 the
  function does not exist and the version reads as 0.
- Recent migrations end with a **self-check block** that raises an exception if expected grants,
  constraints or triggers are missing, so a partial application cannot commit silently.
- [`db/rollback/0026_0025_membership_rollback.sql`](../../db/rollback/0026_0025_membership_rollback.sql)
  is the only rollback script: a destructive last resort for the 0025 and 0026 membership
  migrations, never applied automatically. All other migrations are **forward-only**.

## How hosted databases were migrated

The repository records two methods, both outside `npm run db:migrate`:

- **Supabase MCP `apply_migration`** (0024 production, and earlier rollouts): the reviewed file
  is sent, wrapped in `BEGIN`/`COMMIT`, and recorded in
  `supabase_migrations.schema_migrations`.
- **Supabase CLI `db push`** from a disposable workspace (the M6 rollout of 0008–0011, see
  `db/README.md`).
- **The staging rollouts of 0027–0032** used rehearsed scripts:
  1. a schema comparison against a local replay;
  2. a rehearsal;
  3. a backup;
  4. the migration in one transaction;
  5. post-flight checks;
  6. synthetic end-to-end checks, cleaned back to the baseline.

  They are recorded in [`STAGING_ROLLOUT_0027_0030.md`](../STAGING_ROLLOUT_0027_0030.md) and
  [`CURRENT_WORK.md`](../CURRENT_WORK.md).

Hosted databases therefore track applied migrations in `supabase_migrations.schema_migrations`
(**Inferred** from these records), and from 0030 on also in `private.core_schema_version()`.

## Applying a migration to a hosted environment

This is the procedure the repository documents and has followed. Each step needs the owner's
approval for that environment:

1. **Review** the SQL. It must be forward-only, keep existing rows, and contain no secrets or
   environment-specific values.
2. **Rehearse** on a disposable PostgreSQL 17 database restored from, or replayed to, the target's
   current version. Run the database tests.
3. **Inspect the target read-only**: its current version, any drift from the local replay, and the
   counts and fingerprints of existing rows.
4. **Back up.** The Supabase organization is on the Free plan, with no managed backups or PITR
   recorded (`CURRENT_WORK.md`). The proven recovery artifact is a logical `pg_dump` taken before
   the change and verified with `pg_restore --list`. Store it outside the repository: it contains
   personal data.
5. **Apply** in one transaction, with the self-check at the end.
6. **Post-flight**: version, grants, RLS, routine ownership, and unchanged existing data.
7. **Deploy** the code. On Vercel Production, the release gate refuses to build until the database
   is at the required version.

Restoring from a logical dump is the only rollback path for most migrations. This is
**unverified as a routine operation**: the repository records one successful isolated restore
(`CURRENT_WORK.md`, October 2026) but no production rollback.

### Migration 0033 (Development Cycle 2)

- **Order:** after 0032, then deploy Core, then the website. The previous Core keeps running on a
  schema-33 database: `/v1/health` accepts 33 or later, and the routines the previous Core calls
  remain (the old submission routines, and the recreated membership list with the same signature
  and three appended columns). The previous website keeps working against the new Core, which
  accepts its form for one release.
- **Writes to existing rows:**
  - it backfills `category` and `institution_id` for rows with an `squ.edu.om` email;
  - it makes `university_id` (both tables) and `academic_year` (applications) nullable;
  - it widens the email and storage-key checks.

  It deletes nothing and marks nobody SQU-verified. The self-check fails the migration if anyone
  is.

- **Self-check:** it raises if any of the following is wrong, and the whole migration rolls back:
  - the schema version;
  - FORCE RLS on the ten new tables;
  - a login or browser role able to read them;
  - routine privileges;
  - the evidence-removal trigger.
- **Rollback:** none is scripted.
  - Before members use the new features, restore the pre-migration dump.
  - Afterwards, keep the schema and roll back only the application code. The previous Core works
    on it, but new applications have no student ID, which the previous dashboard shows as empty.
- **Rehearsed** on 2026-11-18 only on a disposable local PostgreSQL 17 replay (all Core database
  tests pass).
- **Applied to staging** on 2026-11-20 with the owner's authorization, after a read-only
  inspection, a drift comparison, a rehearsal of apply and rollback, and a logical backup (see
  [Development Cycle 2](../development-cycle-2.md#staging-application-2026-11-20)). Production is untouched.

### Migration 0034 (committee-level leadership, ADR 0026)

- **Order:** after 0033, then deploy Core, then the website. The previous Core keeps running on a
  schema-34 database: every replaced routine keeps its signature, and the five-argument
  `assign_leadership` remains. The new website needs the new Core.
- **Writes to existing rows:** none. It adds `leadership_appointments.committee_id`, makes `team_id`
  nullable on appointments and requests, adds two unique indexes and the
  `leadership_requests_open` setting (default `true`, the previous behaviour), and widens the audit
  action check.
- **Self-check:** version 34, the scope constraint, the two indexes, no appointment without
  exactly one scope, forced RLS, and routine privileges.
- **Rollback:** a generated script restores the pre-0034 definitions; it refuses once
  committee-level leadership or the switch has been used (roll forward then). Rehearsed locally:
  apply, rollback (schema identical to the 0033 replay), apply again.
- **Applied to staging** on 2026-11-20 with the owner's authorization, after a read-only
  inspection (no drift from the 0033 replay), the rehearsal and a logical backup; post-flight 11 of
  11, and a rolled-back behaviour check on staging (25 of 25, nothing persisted). Production is
  untouched. See [Development Cycle 2](../development-cycle-2.md#committee-level-leadership-0034-2026-11-20).

### Migrations 0035 and 0036 (permissions and Email Centre)

[ADR 0027](../adr/0027-configurable-committee-and-team-permissions.md),
[ADR 0028](../adr/0028-email-centre.md); summary in
[Permissions and Email Centre](../permissions-and-email-centre.md).

- **Order:** 0035, then 0036, then deploy Core, then the website. The new Core requires schema
  36: on a schema-34 database its dashboard fails, because it calls routines 0035 creates. The
  previous Core keeps running on schema 36: every replaced routine keeps its signature, and the
  older forms of `set_verification_settings` and `set_position_limit` remain.
- **0035** adds the permission catalog, the fixed level mapping and per-committee and per-team
  configuration (3 tables), seeds Society Affairs' configuration (11 permissions, replacing its
  slug-based authority), and rewrites the authorization of 65 routines to named permissions. It
  adds `max_holders_per_committee` to positions, set from the team limit, and widens the audit
  action check. Its self-check fails if any routine still tests the Board level directly, or if
  Society Affairs does not have exactly 11 permissions.
- **0036** adds the Email Centre: 5 tables (preferences, suppressions, templates, campaigns,
  deliveries) with forced RLS and their routines.
- **Writes to existing rows:** only the new column on the two position rows. Nothing is deleted.
- **Footprint:** 8 tables, 52 new routines, 76 replaced routines, 6 indexes, 1 column, 1 widened
  constraint.
- **Effect on staging's accounts (2026-11-22):** Board gains `permissions.manage`,
  `settings.verification` and `email.send`; the Society Affairs Committee Manager gains
  `settings.verification`; Technical is unchanged; no leader gains anything (no appointments).
- **Rollback:** a script generated from the target's own schema-34 definitions before applying
  restores them and drops the new objects in order; it refuses once a permission has been changed or the Email Centre used (roll forward then).
  Rehearsed locally from schema 34: apply (schema identical to a 0000–0036 replay), rollback
  (identical to a 0000–0034 replay), apply again.
- **Applied to staging** on 2026-11-22 with the owner's authorization, after a read-only
  inspection (schema 34, no drift in 75 compared routine definitions), a verified backup and the
  rollback script generated from staging; post-flight 15 of 15 (schema identical to a fresh
  replay, existing rows unchanged, every administrator's effective permissions as mapped).
  Production is untouched. The Email Centre was used right after (a member's announcements
  choice), so the rollback script now refuses: roll forward. See
  [Permissions and Email Centre](../permissions-and-email-centre.md#migration-status).

### Migration 0037 (automatic membership approval)

[ADR 0029](../adr/0029-automatic-membership-approval.md).

- **Order:** 0037, then deploy Core, then the website. The new Core requires schema 37. The
  previous Core keeps working on schema 37: every replaced routine keeps its signature, and it
  reads only `code` and `applicationId` from a submission (it reports `pending_review` to the
  website even when the database approved the application).
- **Changes:** the policy check accepts `automatic`; `membership_applications.auto_approved`
  (boolean, default `false`) with `membership_decision_consistency` rewritten; four routines
  replaced (`submit_membership_application_v2`, `get_membership_options`,
  `set_membership_approval_policy`, `get_membership_application`), owners and grants unchanged
  and checked by the migration itself.
- **Writes to existing rows:** the settings row (policy `automatic`, `updated_by` `NULL`) and one
  `membership.policy_changed` audit row with actor kind `migration`. Existing applications keep
  their state; the new column is `false` for them.
- **Rollback:** none scripted. To stop automatic approval, a Technical user chooses another policy
  on `/admin/membership` (audited); the column and the routines can stay.
- **Applied to staging** on 2026-11-22 with the owner's authorization, after a read-only
  pre-flight (14 of 14: schema 36, no drift in the four replaced routines, the two constraints
  found) and a backup of every replaced definition and the settings row; rehearsed first on a local
  schema-36 replay. Post-flight 23 of 23: schema 37, existing applications, members and audit rows
  unchanged apart from the one policy row, the policy `automatic` (previously `single_step`), and
  a behaviour check inside a rolled-back transaction (approved at once, nothing linked before the
  email is confirmed, a member after it, no administrative access, duplicate refused, nothing
  persisted). Production is untouched.

## Adding a migration

1. Record the decision first. The project rule is that new data needs a written decision (an ADR or
   use-case contract) before a schema change.
2. Create `db/migrations/00NN_<name>.sql` with the next number. Add a journal entry with
   `idx: NN`, `version: "7"`, a `when` later than the previous entry, the matching `tag`, and
   `breakpoints: true`.
3. In the SQL:
   - replace `private.core_schema_version()` to return `NN`;
   - create tables in the right schema with `ENABLE` and `FORCE ROW LEVEL SECURITY`, plus a
     `routine_owner` policy, in the **same migration**;
   - write routines as `SECURITY DEFINER`, `SET search_path = public, pg_temp`, owned by
     `uc02_routine_owner`, `REVOKE ALL … FROM PUBLIC`, and `GRANT EXECUTE … TO app_runtime` only
     for entry points;
   - check the actor's live access inside each routine, lock rows you change (`FOR UPDATE` or
     `FOR SHARE`), and write the audit row in the same transaction. Extend the
     `uc02_audit_action_check` list when adding an action;
   - end with a self-check block.
4. Update `db/schema.ts` if the change touches a modeled table, and the documentation (see
   [Documentation maintenance](../maintenance.md)).
5. Add database tests in `tests/db/`, with both allowed and denied cases, run under the real roles.
6. Run `npm run db:check`, `npm test`, `npm run typecheck` and `npm run build` locally.

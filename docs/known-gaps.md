Nothing was fixed as part of the documentation task. Each item says how it was established.

Restarting the dev server cleared it, and a fresh server stays stable through edits and writes to build folders. Production has no hot reload. ## Missing features and incomplete flows

- `public.certificates`, `public.archive_items` and `public.mentorship_connections` exist from the
  original model, but no code issues certificates, manages the archive or handles mentorship. The
  website's certificate and network pages are Coming Soon prototypes.
- No transition into or out of `graduate`.
- No membership suspension (ADR 0024: no approved policy).
- No automatic expiry or deletion of applications, members or records: intentionally excluded by
  the owner.
- The public event DTO has no type, end time, capacity counts, disciplines, programme or Arabic
  text. The website keeps those designs hidden.
- No scheduled jobs and no webhooks: there is no on-demand revalidation signal to the website, and
  the Storage queue drains opportunistically.
- Administrators' Auth sessions cannot be invalidated by Core when access is revoked. Authorization
  still ends on the next request (ADR 0014).
- **Email Centre delivery is unverified live.** No provider, sender address or secret is
  configured (owner decision: deferred), so sending is off in every environment. Only the test
  adapter has sent messages (unit, database and browser tests). Provider webhooks (delivered,
  bounced, complained) are not wired: `private.email_record_event` exists but nothing calls it, so
  messages stay "accepted" and bounces are not suppressed automatically. No scheduler calls
  `/v1/internal/email-dispatch` yet, so a campaign sends only while someone has its page open.
- **What each personal level includes is fixed** by migration 0035. Changing it needs a new
  migration; Administration → Permissions edits committees and teams only.
- **The browser harness runs `next dev`.** First visits to a route compile it and can reload the
  page under a test; specs retry such aborted navigations once. Production builds do not do this.

## Recommendations

These are suggestions, not decisions:

1. Resolve the production Supabase project question with the owner first. It affects data
   protection and every rollout note.
2. Drain the Storage deletion queue independently of the membership bucket and of reviewer
   activity, for example with an authenticated maintenance trigger.
3. Enable `CORE_API_HOST_ENFORCEMENT` once both hostnames are confirmed, and set `APP_ORIGIN` to
   the dashboard's canonical host.
4. Add the project endpoints and current servers to `openapi.v1.yaml`. Update the stale README,
   `CLAUDE.md` status, `db/README.md` and ADR 0024 header.
5. Add `CORE_API_ALLOWED_ORIGINS` and `CORE_API_HOST_ENFORCEMENT` to `.env.example`. Mark
   `RESEND_API_KEY` as unused or remove it.
6. Bring `db/schema.ts` in line with the migrations, or document it as intentionally partial at
   the top of the file.
7. Revoke `EXECUTE` on the unused `register_for_event` in a future migration, if nothing external
   depends on it.
8. Consider extending `/v1/health` (or a separate check) to report Auth and Storage reachability
   without disclosing configuration.
